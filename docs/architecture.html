DownloadKit: Architecture

PROPOSAL  A Swift package for reliable, resumable, background-capable file downloads on iOS and macOS. There is no code yet; this is the target design.

1. Summary

DecisionChoiceWhy
TransportOne URLSession with background configuration (plus an optional foreground session)Downloads keep going while the app is suspended or killed by the system
Concurrency modelDownloadManager is an actor; events go out as AsyncStreamThread-safe state without locks; works naturally with SwiftUI and async/await
SchedulingOwn priority queue with a maxConcurrent limit, instead of handing every task to URLSessionSupports priorities, Wi-Fi-only rules and fair ordering. URLSession alone gives none of these.
PersistenceTask records + resume data on disk (JSON files in Application Support)Restores the queue after the app relaunches and resumes partial downloads
ReliabilityRetry with exponential backoff, resuming from resume data; optional checksum checkSurvives flaky networks without starting over from 0 bytes
PlatformsiOS 16+, macOS 13+, Swift 6 toolchain (strict concurrency), no dependenciesData-race safety checked by the compiler; easy to adopt

ComponentJobNotes
DownloadManagerPublic entry point; owns all stateAn actor. Removes duplicates by URL + destination, so enqueuing the same file twice returns the existing task.
DownloadTaskHandle the app keeps hold ofSendable struct; exposes events: AsyncStream<DownloadEvent>
SchedulerDecides what runs nextOrders by priority, then FIFO. Checks network rules (Wi-Fi only, low-data mode) before starting.
SessionCoordinatorWraps URLSession and its delegateThe delegate is nonisolated and passes events on to the actor. Moving the file must happen synchronously inside didFinishDownloadingTo.
TaskRegistryMaps URLSession tasks to DownloadKit IDsSaves the ID in URLSessionTask.taskDescription so the mapping survives a relaunch.
FileMover / ValidatorPuts the finished file in place and checks itMoves the file atomically, then checks the expected size and optional SHA-256.
RetryPolicySorts errors into retry vs. give upRetries timeouts, lost connections and 5xx. Gives up on 4xx and on cancellation.
TaskStore / ResumeDataStoreSaves state to diskWrites on every state change and throttles progress writes (about once per second).

3. Download flow

What happens from enqueue to a finished file, including retries.

  B -->|yes| B1["Return existing DownloadTask"]
  B -->|no| C["Create TaskRecord, state = queued"]
  C --> D["Persist to TaskStore"]
  D --> E["Scheduler.insert by priority"]
  E --> F{"Free slot and network rules OK?"}
  F -->|no| F1["Stay queued; wait for slot or path change"]
  F1 --> F
  F -->|yes| G{"Resume data stored?"}
  G -->|yes| H["session.downloadTask(withResumeData:)"]
  G -->|no| I["session.downloadTask(with: request)"]
  H --> J["Tag task with ID, resume(), state = downloading"]
  I --> J
  J --> K["didWriteData: emit progress (throttled)"]
  K --> L{"Finished OK?"}
  L -->|yes| M["didFinishDownloadingTo: move temp file now (sync)"]
  M --> N{"Validator passes?"}
  N -->|yes| O(["state = completed, emit .finished(fileURL), free slot"])
  N -->|no| P["Delete file, error = validation failed"]
  L -->|no| Q["didCompleteWithError"]
  P --> R
  Q --> Q1["Save resume data if present"]
  Q1 --> R{"RetryPolicy: retry? attempts left?"}
  R -->|yes| S["state = waitingToRetry, backoff 2^n s plus jitter"]
  S --> E
  R -->|no| T(["state = failed, emit .failed(error), free slot"])
  O --> E2["Scheduler picks next task"]
  T --> E2

4. Task lifecycle

Every DownloadTask is in exactly one of these states. completed and cancelled are final; failed can be retried by the app.

stateDiagram-v2
  [*] --> queued: enqueue
  queued --> downloading: slot free
  downloading --> paused: pause (keep resume data)
  paused --> queued: resume
  downloading --> waitingToRetry: retryable error
  waitingToRetry --> queued: backoff elapsed
  downloading --> completed: file moved and valid
  downloading --> failed: fatal error or no attempts left
  queued --> cancelled: cancel
  paused --> cancelled: cancel
  downloading --> cancelled: cancel
  waitingToRetry --> cancelled: cancel
  failed --> queued: retry() by app
  completed --> [*]
  cancelled --> [*]
  failed --> [*]

5. Background and relaunch

The system keeps downloading after the app is suspended or killed, then relaunches it in the background so DownloadKit can finish up.

sequenceDiagram
  participant App as AppDelegate
  participant DM as DownloadManager
  participant SC as SessionCoordinator
  participant OS as nsurlsessiond
  participant TS as TaskStore

  Note over App,OS: App suspended or killed while downloads run in the system daemon
  OS->>App: relaunch, handleEventsForBackgroundURLSession(id, completion)
  App->>DM: handleBackgroundEvents(id, completion)
  DM->>TS: load task records
  DM->>SC: recreate URLSession with the same identifier
  SC->>OS: getAllTasks
  OS-->>SC: running and finished tasks
  SC->>SC: re-map tasks via taskDescription
  OS->>SC: didFinishDownloadingTo (per finished task)
  SC->>SC: move file, validate
  SC->>DM: completed(id, fileURL)
  DM->>TS: persist state = completed
  OS->>SC: urlSessionDidFinishEvents
  SC->>DM: background events done
  DM->>App: call stored completion handler on main thread

6. Public API sketch

public actor DownloadManager {
    public static let shared = DownloadManager(configuration: .default)
    public init(configuration: DownloadConfiguration)

    @discardableResult
    public func enqueue(_ url: URL,
                        to destination: URL,
                        priority: DownloadPriority = .normal,
                        checksum: Checksum? = nil) async -> DownloadTask

    public func pause(_ id: DownloadTask.ID) async
    public func resume(_ id: DownloadTask.ID) async
    public func cancel(_ id: DownloadTask.ID) async
    public func retry(_ id: DownloadTask.ID) async
    public func tasks() async -> [DownloadTask]

    /// Call from application(_:handleEventsForBackgroundURLSession:completionHandler:)
    public nonisolated func handleBackgroundEvents(identifier: String,
                                                   completion: @escaping () -> Void)
}

public struct DownloadTask: Identifiable, Sendable {
    public let id: UUID
    public let url: URL
    public let destination: URL
    public var state: DownloadState { get async }
    public var events: AsyncStream<DownloadEvent> { get }
}

public enum DownloadEvent: Sendable {
    case stateChanged(DownloadState)
    case progress(received: Int64, expected: Int64)
    case finished(URL)
    case failed(DownloadError)
}

// Usage
let task = await DownloadManager.shared.enqueue(videoURL, to: localURL, priority: .high)
for await event in task.events {
    if case .progress(let got, let total) = event { progress = Double(got) / Double(total) }
}

8. Risks to design around

RiskMitigation
The temp file is deleted as soon as didFinishDownloadingTo returnsMove it synchronously inside the delegate callback, never in a Task { } that runs later
Background sessions can't use completion-handler APIs and ignore some settingsUse the delegate only; keep the foreground session for small, urgent files
Resume data is only valid if the server supports range requests and ETagsIf resuming fails, fall back to a full restart; record that the server doesn't support resume
The system may throttle background downloads (isDiscretionary)Expose it as a per-task option; default to false for downloads the user started
Two session objects with the same background identifierCreate the session once inside SessionCoordinator and never expose it
